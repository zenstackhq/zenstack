# @zenstackhq/migration

ZenStack's native database schema migration engine.

It diffs stable JSON snapshots of a compiled ZenStack schema to author migrations, and
runs them with [Kysely](https://kysely.dev)'s migrator. Each migration is a folder:

```
migrations/
  20260101000000_init/
    snapshot.json         # stable schema snapshot after this migration
    migration.ts          # exports `migrate(db)` (+ optional before/afterMigrate)
```

Migrations are forward-only (no down migrations); recovery is done by rolling forward.

## Programmatic usage

The engine behind the `zen migrate` / `zen db push` CLI commands is available as a library.
Construct it with a compiled schema (the `schema.ts` generated by `zen generate`), a
migrations directory, and a connection URL:

```ts
import { MigrationEngine } from '@zenstackhq/migration';
import path from 'node:path';
import { schema } from './zenstack/schema'; // compiled by `zen generate`

const engine = new MigrationEngine({
    schema,
    migrationsDir: path.resolve('migrations'),
    connectionUrl: process.env['DATABASE_URL']!,
});
```

### Author and apply a migration (`migrate dev`)

`generate` diffs the latest snapshot against the current schema and writes a new migration
folder (without applying it); `deploy` applies all pending migrations:

```ts
const result = await engine.generate('add-user-profile');
if (result.aborted) {
    // the confirmDataLoss hook declined the destructive changes
    throw new Error(`migration aborted:\n${result.warnings.join('\n')}`);
}
if (result.created) {
    console.log(`created ${result.name}`); // e.g. 20260101000000_add_user_profile
}

const deployed = await engine.deploy();
if (deployed.error) {
    throw deployed.error;
}
```

Two optional hooks control how `generate` handles ambiguous or destructive changes (the CLI
wires interactive prompts into these; headless callers can supply their own logic or omit
them for the safe defaults — every rename stays a drop + create, and destructive migrations
generate without confirmation):

```ts
const engine = new MigrationEngine({
    schema,
    migrationsDir,
    connectionUrl,
    // disambiguate "X disappeared, Y appeared" into data-preserving renames;
    // anything not returned stays an independent drop + create
    resolver: {
        resolveTableRenames: ({ created, deleted }) => [{ from: 'User', to: 'Account' }],
        resolveColumnRenames: ({ table, created, deleted }) => [],
        resolveEnumRenames: ({ created, deleted }) => [],
    },
    // called with human-readable warnings when the migration can destroy data;
    // return false to abort (generate() then resolves with { aborted: true })
    confirmDataLoss: async (warnings) => askTheUser(warnings),
});
```

### Deploy in production (`migrate deploy`)

```ts
const result = await engine.deploy();
if (result.error) {
    throw result.error;
}
for (const r of result.results ?? []) {
    console.log(`${r.status}: ${r.migrationName}`);
}
```

`deploy` refuses to run if an already-applied migration's `migration.ts` was edited after
the fact (checksum mismatch); pass `ignoreChecksumMismatch: true` in the options to override.

### Check migration status

```ts
for (const m of await engine.status()) {
    console.log(`${m.name}: ${m.applied ? 'applied' : 'pending'}`);
}
```

### Prototype without migration files (`db push`)

`push` introspects the live database and applies the DDL to make it match the schema —
no migration folders, no history:

```ts
const pushed = await engine.push({ acceptDataLoss: false });
if (pushed.aborted) {
    console.log('blocked by potential data loss:', pushed.blocked);
}
```

### Adopt an existing database (`migrate baseline`)

For a database that already matches the schema (e.g. previously managed by Prisma migrate),
record the current state as a single already-applied migration, so future `generate` calls
diff forward from it:

```ts
await engine.baseline();
```

Related recovery primitives: `engine.resolveApplied(name)` marks a migration as applied
without running it (after rolling it forward by hand), and `engine.reset()` drops all
tables and re-applies the whole history from scratch (development only — all data is lost).
